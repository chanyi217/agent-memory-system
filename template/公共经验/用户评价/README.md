# 用户评价

> **这份文件是为了什么**
>
> **目的**：记录"以前这么做被夸/被否过"，让下次开工前能对一眼。
>
> **不做会怎样**：同一类错误会在不同项目里反复犯，每次都像是第一次。

---

## 零、使用约定（**先读这一节，再读条目**）

**评价不是判决书，是一条带上下文的观察记录。** 它记的是"那次、那个场景下，他否掉了什么"——换个场景，同一个做法可能正是对的。

### 三条硬约定

**① 默认是用，审视是为了发现不适用的部分，不是找理由不用。**
一看到"可能不对"就绕开，等于白记。

**② 不靠谱性超过三成的，不用。**
估一下「这条大概有多大可能是错的或不适用」——超过 30% 就先放下。
但**不用也要说明为什么不用**：「`XX-日期-标题` 那条我没采纳，因为……」。不采纳不是问题，不说明才是。

**③ 大方向的指导，必须问用户。**
如果这条评价决定的不是一个具体动作，而是**一个方向**（整体风格、架构选型、受众定位、这条路还要不要走），**不要自己按评价定**——把评价摆出来，说清"它建议 X / 我判断它在这次适用或不适用 / 代价是 Y"，让人拍板。

### 怎么估「不靠谱性」（三问）

| 问 | 不靠谱的信号 |
|---|---|
| ① 场景还是一类事吗 | 技术栈变了、受众换了、目标变了、时间过去很久规则已改 |
| ② 依据实不实 | 没有原话、没有出处、说不清"为什么成立"——三样都缺，可信度很低 |
| ③ 当时的判断有没有被后来的事推翻 | 有相反的评价，或者那次的做法后来被证明是对的 → 降权 |

两问答"不靠谱"，就不采用。
