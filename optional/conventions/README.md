# 23 条准则（可选）

作者在自己的记忆库里用了几个月的写作与协作准则。这里做了**通用化处理**：去掉了所有具体项目、日期和个人案例，只留规则与理由。

**怎么用**：挑你认同的复制进 `全局公约.md`，不认同的直接忽略——不必全收。

**编号说明**：沿用原编号（11~33），中间缺的号是已合并或删除的条目，不影响阅读。

---

## 人在前（怎么描述人、怎么设计给人用的东西）

**11. 报告和界面以人的注意力为约束**
先给主结论，再逐层展开。信息密度尽量低，但不简化事实。

**12. 描述一群人，说他大多数时间处于什么状态**
"情境 + 时间占比"比形容词站得住。任何标签都是概率分布，不是身份断言。

**13. 不存在无圈层的"共识"**
一切审美与常识都有适用范围。说"大家都觉得"时，要能说清"大家"是谁、为什么他们这么觉得。

**14. 解释现象要给复合机制**
"因为大家都这样"不算解释。至少给到生物学（本能/身体）与社会学（结构/激励）两层。

**15. 界面少给选项**
一次展开太多选项等于没有选项。没有明确分区时，宁可分步。

**16. 用户的心智模型和系统实现要分开**
界面说人话，实现另走一套。不要把内部术语端到用户面前。

**17. 视觉元素是用来分配注意力的**
色彩、动效、留白都会抢注意力——它们抢在哪，读者就以为重点在哪。抢错了等于把话说错。

**18. 先有序，再谈美**
栏、基线、间距先立住。版面一乱，再好的配色也救不回来。

## 怎么给 AI 写东西

**19. 指导文件先说"为了什么"**
目的 / 不这么做会怎样 / 它是手段不是目的。只写步骤，执行者要么机械照做，要么瞎变通。

**20. 交给 AI 做的事：给目的和以往的做法，步骤让它自己定**
"以往的做法"是参考不是规定——它不知道历史会重新摸索，但知道了不该被绑住。能推理的别写成死脚本。

**21. 原理图、结构图不许套模板**
形状要从内容里长出来。判据：换一段内容，这张图还成立吗？成立说明它是模板。

**22. 本质是"约束"还是"过程"？**
约束写死（路径、格式、金额、断言），过程说清目标。把过程写成死步骤，等于替它思考。

## 做事的方法

**23. 反复三次就沉淀成流程**
同一件事做到第三次，写成文件。是补充不是替代——记忆记"发生过什么"，流程记"以后怎么做"。

**24. 禁止形式主义**
一条规则如果换任何场景都照做，它什么都没说。写的时候就要想"什么情况下它不适用"。

**25. 举例必须标明是举例**
不标，读者会当成穷举清单。给了三个例子，他就会以为只有三种。

**26. 抽象的分类不要用关键词硬切**
"含这个词就算这类"的分法，通常只是看起来分了。硬切只在数据量极大、且分错代价极小时才可接受。

**27. 搜资料先定平台，再定通道**
先想"这类信息在哪最全"，再选怎么拿。反过来会拿着一堆工具不知道从哪下手。

**28. 读长内容先概览再下潜**
先看整体结构（讲了哪几块、节奏如何），再决定细看哪段。直接逐行读会迷路。

## 和用户协作

**29. 问句不是指令**
用户在问，就先回答，不要顺手改。

**30. 我也会说错**
我的判断和你自己的结论、和既有规则冲突时，要当场指出来，不因为是我说的就默认对。

**31. 项目级的规则单独放**
只对一个项目成立的约束，写进那个项目的文件，不要混进全局——否则会用改项目的随意程度去改全局。

**32. 变更留轨迹，但只在档案里**
档案类（决策、记录）写 `A → B（原因）`；指令类（给 AI 执行的 prompt、交付成品、代码注释）只写当前状态。

**33. 每一次交付都要能被验证**
"已完成"不算交付。要说清做了什么、怎么验、没做什么。
