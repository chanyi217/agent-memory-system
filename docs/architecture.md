# 架构说明

这份文档解释"为什么这样分"，而不是"每个文件夹放什么"（那是每层 README 的事）。

---

## 零、先划清边界：它不是 harness

**harness** 是模型之外的**运行时**：主循环、工具、上下文压缩、权限门、沙箱、checkpoint。
Claude Code、Codex CLI、OpenHands、Aider 都是 harness。

**这套东西是记忆协议**，不含任何运行时——它不会替你调工具，也不会拦你的操作。

一句话分工：

> **harness 管「这一次怎么跑稳」，这套管「下一次不重犯」。**

两者记的东西根本不同：

| | 记什么 | 用途 |
|---|---|---|
| harness 的记忆（transcript） | 这次聊了、做了哪些动作 | 重放、续跑 |
| 这套东西 | 目标为什么变成这样、哪些做法被否过 | 防回退、防重犯 |

**所以别指望它做 harness 的事**（强制拦截、上下文压缩），
也确实存在 harness 做不到的事（跨工具、跨会话、跨人传递决策）——那才是它存在的理由。

> 详细对照见仓库根目录 README 的「它和 agent harness 是什么关系」。

## 一、三层结构

```
            规则层（怎么做）
       ┌───────────────────────┐
       │ 工作流 / 公约 / 工具表  │  ← 对"所有事情"成立
       └───────────┬───────────┘
                   │
            资产层（可复用）
       ┌───────────────────────┐
       │ 手册 / SOP / 技法 / 评价│  ← 对"多个项目"成立
       └───────────┬───────────┘
                   │
            项目层（具体工作）
       ┌───────────────────────┐
       │ 档案 / 公约 / 资产      │  ← 只对"这一个项目"成立
       └───────────────────────┘
```

**为什么必须分三层，而不是一个文件夹装所有？**

因为**适用范围不同，修改代价也不同**。

- 改一条全局规则 → 影响所有项目，要谨慎；
- 改一条项目公约 → 只影响这个项目，可以大胆；
- 混在一起，人就会用修改项目文件的随意程度去改全局规则。

---

## 二、一次完整工作

```
① 开工
   读入口 → 读清单 → 读本项目档案/公约 → 读本次相关的手册
   ↓
② 做事
   遇到不确定 → 查评价（以前被否过吗？）
   ↓
③ 交付
   用户提问原文 / 验收清单 / 交付物入库
   ↓
④ 回流
   这次的判断 → 写进档案（为什么）/ 写进评价（被否定过什么）
   ↓
⑤ 呈现（可选）
   扫描成可视化索引，方便回溯
```

④ 是整套东西里最关键的一环，也是大多数知识库缺的一环。

**没有回流会怎样**：规则越写越多，教训越记越散，两者永不相遇。下次开工只读规则，读不到教训，同样的错再犯一遍。

## 三、文件之间的依赖方向

```
README（入口）
   └→ 开工清单
        ├→ 规则（工作流 / 公约 / 工具表）
        ├→ 评价索引 ←── 评价条目
        ├→ 项目档案 / 项目公约
        └→ 手册（按事分包）

项目档案 ──引用──→ 验收清单
项目公约 ──引用──→ 全局公约（"此处与全局第 N 条不同"）
手册 ──引用──→ 工作流（"流程见 X"）
```

**依赖是单向的**：下层可以引用上层，上层不引用下层。

原因：如果全局规则引用了某个项目，那个项目一删，全局就断了；反过来项目引用全局，删项目不影响全局。

---

## 四、为什么"入口"和"规则"要分开

入口（README）只回答一个问题：**我该看哪份？**

它不写规则。规则在工作流和公约里。

这看起来啰嗦，但解决了一个真实问题：**规则会膨胀，而索引的膨胀速度慢得多**。

如果把规则和索引混在一起，半年后打开文件，前 200 行是"为什么"，中间是规则，最后才找到"该看哪份"——人会直接关掉。

---

## 五、负面资产的独立价值

大多数知识管理记的是"我做过什么"。

这里额外记一类：**"这条路走不通，以及为什么"**。

它有独立的目录，独立的使用约定（见 `公共经验/用户评价/README.md`），因为：

1. **它只存在于特定的人机交互里**——"这个方案在这个项目上被否了"，从外部搜不到；
2. **它容易被遗忘**——成功会被反复引用，失败会被悄悄绕过；
3. **它有保质期**——场景变了，旧结论可能失效。所以要用之前先审视（不靠谱性超过三成就别用，大方向不确定就问用户）。

## 六、这套结构的已知弱点

写在这里，因为它决定了你该不该用它。

| 弱点 | 后果 | 缓解 |
|---|---|---|
| 依赖 AI 主动读文件 | 不读就全失效 | 开工清单写死第一步；能用 hook 的地方加 hook |
| 目录会逐渐失序 | 半年后自己也找不到 | 每层 README + 定期归位 |
| 索引漏项 = 永久失联 | 某类文件永远读不到 | 每新增一类文件，必须同步索引 |
| 无强制力 | 规则写了不执行 | 这是它跨工具的原因，也是它的上限 |

**它不是 harness**：harness 保证"某个操作做不了"，这套东西只保证"该看的都写了"。要强约束，得在 harness 层另做。

---

## 七、什么时候不值得用

- 项目只做一次、不会回头 → 直接做，别建库
- 做的事高度重复、流程固定 → 写成脚本比写文档好
- 只有你一个人、且你记性极好 → 成本大于收益

**它适合的是**：同一个项目反复推进几个月、中间会中断、且中途会换对话/换工具的场景。
